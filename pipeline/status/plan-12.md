## 1. P0 — セキュリティ（今回すべて実装する）

### S1. セッションを無効化する方法が無い
- 根拠: `auth.ts:14` トークンは **30 日**。`verifySession` は署名と `sub` しか見ない。
  クライアントの `signOut`（`store.tsx:467`）は**ローカルのトークンを捨てるだけ**。
- 影響: 端末の紛失・共有 PC・トークン漏洩のいずれでも、**取り消す手段が利用者にも運営にも無い**。
  設定画面の「サインアウト」は、盗まれた端末に対しては嘘をついている。
- 実装: `User.tokenVersion`（Int）。JWT に `v` を載せ、`requireAuth` で突き合わせる。
  `POST /v1/auth/sign-out { allDevices }` — `true` で version を進めて**全トークンを即時失効**。
  アカウント削除でも進める。クライアントに「すべての端末からサインアウト」を追加。

### S2. セキュリティヘッダが 1 つも無い
- 根拠: `grep` で `x-content-type-options` / `referrer-policy` / `strict-transport-security` /
  `content-security-policy` が API に 0 件。
- 影響: 共有ページ `/s/*` は**この製品で唯一の HTML** で、CSP も `frame-ancestors` も無い
  = クリックジャッキング可能。JSON API 側も MIME スニッフィングと referrer 漏洩が素通り。
- 実装: 全レスポンスに `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`,
  `Permissions-Policy`, 本番のみ `Strict-Transport-Security`。共有 HTML には専用の CSP
  （`default-src 'none'`、自分の img と inline style だけ許可）。

### S3. リクエストボディに上限が無い
- 根拠: `bodyLimit` 相当のミドルウェアが無い。zod は**バッファされた後**に検証する。
- 影響: 100MB の JSON を投げるだけでプロセスのメモリを食える。認証前でも通る面がある。
- 実装: 既定 64KB の body limit ミドルウェア（413）。`/billing/webhook` は別枠。

### S4. LLM 呼び出しにタイムアウトが無い
- 根拠: `modes/live.ts` の `messages.create` に `AbortSignal` 無し。SDK 既定は 10 分。
- 影響: 上流が詰まると**リクエストとエネルギー 1 点を 10 分間人質に取られる**。
  ユーザーは「投稿が返ってこない」を見続け、リトライでさらに課金が増える。
- 実装: tier ごとのタイムアウト（light/mid は数十秒、high は長め）。超過は既存の
  `GeneratorFailure("error")` に落ちる = フォールバック + エネルギー返却。

### S5. 依存監査 — 26 件、うち**本番依存は `hono` の 2 件**
- 根拠: `pnpm audit` = critical 1 / high 12 / moderate 12 / low 1。ただし
  `shell-quote`(critical) は react-devtools、`vite`/`vitest`/`eslint`/`@expo/cli` は
  ビルド・テスト専用。**実行時に外部入力を受けるのは `hono` だけ**（<4.13.11 で
  serveStatic の二重デコード、hono/jsx の XSS。どちらも当該機能を使っていないが、
  本番依存に既知の勧告を残す理由が無い）。
- 実装: `hono` を `>=4.13.11` へ。CI に**実行時依存だけを対象にした** audit ゲートを追加
  （dev 依存の勧告で CI を赤くしても、誰も読まなくなるだけなので分ける）。

## 2. P1 — 本番に要る機能（今回実装する）

### F1. 「すべての端末からサインアウト」（S1 のクライアント側）
API だけ作ってボタンが無ければ、利用者にとっては存在しないのと同じ。

### F2. プッシュ通知をオフにできない
- 根拠: `routes/push.ts` は `POST /register` **のみ**。解除エンドポイントも設定の
  トグルも無い。
- 影響: 「While you were away」を送る製品で、**アプリ内に off スイッチが無い**。
  OS の設定しか逃げ道が無く、同意の撤回手段としても弱い。
- 実装: `POST /v1/push/unregister`（この端末 / 全端末）+ 設定画面のトグル。

## 3. 洗い出したが、今回は実装しないもの（理由つき）

| 機能 | なぜ今回やらないか |
|---|---|
| メールアドレスの変更 | アカウント復旧の設計（所有確認 2 通、旧アドレスへの通知、乗っ取り時の巻き戻し）が要る。片手間で入れると**乗っ取り経路そのもの**になる |
| 2 要素認証 | ログインが「メールに届く 6 桁」なので、2FA の 2 要素目が 1 要素目と同じ経路になる。意味を持たせるには認証方式ごと変える必要がある |
| Web クライアントの CSP | Expo の静的エクスポートは**配信側（CDN/ホスティング）でヘッダを付ける**のが正道。リポジトリ内の変更では完結しない |
| トークンを localStorage から出す | XSS 耐性は上がるが、cookie にすると CSRF 対策一式と SSE の認証方式変更が連鎖する。**S1 の失効手段**の方が費用対効果が高い |
| 監査ログ（誰が何を見たか） | モデレーション決定は第10次で人に紐づいた。閲覧ログは**保存する以上は守る対象が増える**ので、運用体制が決まってから |
| レート制限の per-route 細分化 | 現行 5 区分で実測が無い。**実データ無しの細分化は勘**であり、`shared` ストアになった今は後から安全に変えられる |

## 5. 「本番反映」について

このリポジトリには**デプロイ先が無い**（ホスティング・ドメイン・`ANTHROPIC_API_KEY` のいずれも）。
したがって今回到達できる最大は「`main` にマージできる状態にして、リリース手順を実行可能な形で置くこと」
であり、それ以上を「本番反映した」と言うのは嘘になる。実際にやること:

- ブランチを緑にして push（毎回やっている）
- `docs/deploy.md` のリリース手順を、今回追加した設定も含めて完全な状態に保つ
- PR の作成はユーザーの明示的な指示があるときだけ（CLAUDE.md / 運用ルール）

## 7. 実装中に見つけたもの

- **`Number("") === 0`。** ボディ上限の最初の実装は `content-length` 欠落を「0 バイト」と読み、
  ストリーム本文が全部素通りしていた。ヘッダ付きのテストは通り、ストリームのテストが落とした。
- **Hono のミドルウェアは `next()` の後の `return` を見ない。** 413 を返したつもりが、
  `parseBody` が先に返した 400 がそのまま出ていた。`c.res` に代入するのが唯一の方法。
- **削除時のセッション失効で、既存の 4 ケースが赤になった。** 直すべきはコードではなくテストだと
  判断した根拠: 出荷済みクライアントは削除直後に**ローカルでサインアウトしている**
  （`app/delete-account.tsx`）ので、「削除に使ったトークンで復元する」経路は実在しない。
  一方で `requireAuth` は soft-delete されたアカウントを `/account/restore` **だけ**通すので、
  盗んだトークンで**削除を取り消せる**。テストは「入り直してから復元する」に更新し、
  元の表明（410 + `ACCOUNT_DELETED`、開いている唯一の扉、猶予期間、purge）は 1 つも落とさず、
  さらに「古いトークンが死んでいること」を各ケースに足した。弱めてはいない。
- **CI の lint は元から赤だった**（14 errors）。`format:check` をブロッキングにした第11次の後も、
  lint が赤のままなら CI は一度も緑になれない。14 件ともルール無効化ではなく**原因側**で直した。
