# 残課題の対応(2026-09-04 後半)

`pnpm --filter api test` **263/263** · `pnpm --filter @rpgllm/llm test` **135** · `pnpm e2e` **47 passed / 4 skipped / 0 failed** · 全 typecheck 緑。

## 1. Batch ティア — **解消**(設計上唯一の未達だった項目)

Message Batches API 経路を実装し、結果は `custom_id` で突き合わせる(順序では対応付けない)。待たされる人がいない生成(雑談 G2 / 記憶統合 G7 / 不在ダイジェスト G10 / 審査 GJ)をここに載せ、**スケジューラが呼ぶのはバッチ版**にした。即時性が要る `GET /v1/digest` と `GET /v1/memory/:id` は対話版のまま(バッチは 24 時間 SLA)。

実測(クリーンな DB で雑談補充ジョブを実行):

| レーン | 呼び出し | コスト | 生成数 |
|---|---|---|---|
| batched | 5 | $0.013905 | 52 投稿 |
| interactive | 3 | $0.055853 | 12 投稿 |

定価 $0.027808 → 請求 $0.013905、**実現割引 50.0%**(期待値どおり)。

副産物: G2 / G10 / GJ はこれまで G1 の合成プロンプトで代用されていたが本物の生成器になり、審査員が指定どおり Opus 5 で動くようになった(それまで黙って Sonnet に落ちていた)。

## 2. Thompson sampling — **解消**

固定 50/50 をやめ、Beta 事後分布による割当に。報酬は `quality − 0.4 × (cost / champion cost)` を 0..1 にクランプ。👍=1、👎/再生成/フォールバック=0、未評価=0.6(未評価を 0 にすると沈黙が失敗に見える)。割当はユーザー単位で固定(エンゲージメント指標が混ざらないため)、探索の下限あり。ガードレール違反で腕を自動停止、昇格には**呼び出し数・確信度・オフライン評価の 3 つ**が揃うことを要求し、`PromotionEvent` に根拠を残す。再生成呼び出しとバッチ行は集計から除外している。

## 3. オフライン評価 — **解消**

生成器ごとに 50 件の凍結セット(うち 15 件は手書きの難問: 流出ドラマ、失恋、日本語敬語、罵倒入力、境界的な自傷ケース、英日)。機械判定 40% + 審査員 60% で採点し、`EVAL_GATE` で昇格可否を決める。CLI は `node scripts/eval.mjs --generator G1`。

## 4. スケジューラ — **解消**

`pnpm --filter api worker` が 7 ジョブを cron で実行。**ジョブ名ごとに Postgres の助言ロック**を取るので、ワーカー二重起動や再デプロイの重なりで二重実行にならない。実行記録は `JobRun` に残り `GET /v1/jobs` で読める。失敗してもループは生き、SIGTERM で実行中を待って終了。

## 5. 認証コードの永続化 — **解消**

プロセス内 Map から Postgres へ。**API を複数インスタンスで動かせるようになった**。ソルト付きハッシュのみ保存、10 分、5 回、使い捨て、定数時間比較、1 アドレス 1 有効コード。

## 6. 連続ログインのカラム化 — **解消**

台帳からの導出をやめ `User.streakDays` 等を正本に。既存記録は初回読み出し時に移行。エネルギー上限のキャップは維持。

## 7. 課金 — **解消**(ただし実ストア未接続)

RevenueCat の Webhook が署名検証つきで本物に。イベント適用は一意なイベント ID を含む単一トランザクションで冪等。**返金は即時剥奪、キャンセル/期限切れは期間終了まで、決済リトライは猶予期限まで**。権利判定を 1 関数に集約し、エネルギー上限と広告可否がそこを経由する。復元はクライアントの申告 ID を信用せず、サーバが知る ID のみで照合する。

## 8. プッシュ配信 — **解消**(ただし認証情報未設定)

権限要求は**最初の投稿成功後**(起動直後に求めるのが拒否率を上げる最大の原因)。100 件ずつ送信、無効トークンを削除、23-8 時は送らない、日次上限あり。受領確認は非同期に埋まるため専用ジョブが 20 分ごとに後追いする。

## 9. テスト分離 — **解消**

実行ごとに専用 DB を作って捨てる。Web サーバが node を直接起動するようになり、SIGTERM が握り潰されてポートに API が残る問題も解消。

# 第4次: 世界そのものが足りない(2026-09-05)

前の3次はすべて「既にある世界を、どう良く見せ、どう安く回し、どう課金するか」の話だった。
そこを詰めきった結果、いちばん大きな穴が残っていることが見えた — **世界が3つしかない**。

## 10. ワールド生成 — **解消**

`05-ai-features.md` は「AIF-014 (G9) 実装済み」と書いていたが、これは誤記だった。
`packages/llm/src/generators/` に g9 は無く、3つの世界は手書きの TypeScript で、
新しい世界を足すには人間がバイブルを2ロケール分書くしかなかった。teardown で見た Status の
「13M ワールド」に対して、こちらは 3。桁が違うのではなく、種類が違う。

G9 を5段階に分けて実装した(concept/bible は high、cards/events は mid、texture は light)。
1 ワールド 14 呼び出し、**約 $0.32**。段階3〜5 は 4,389 トークンの共通接頭辞を共有するので、
11 呼び出しのうち 10 はキャッシュ読み出しになる(Haiku 4.5 の 4,096 下限を意識した設計)。
replay では API キー無しで全 8 ジャンル・2 ロケールが 4,400〜4,900 トークンのバイブルを出す。

## 11. ユーザー作成ワールド(AIF-003)— **解消**

B(チームが生成器で世界を量産する)だけでは、Status の「13M ワールド」には永久に届かない。
A(プレイヤー自身が作る)の動線も同時に作った。1 行 + ジャンル → 120 ジェム → 生成ジョブ → 完成。

安全性は 2 段構え。プレミスはシステムプロンプトの一部になるので、**生成前に**落とす
(ジェムもトークンも消費しない)。生成物は**公開前に**もう一度 G8 にかけ、`public` は必ず人間の
審査を通す。`private` は即座に遊べて、どの一覧にも出ない。`unlisted` はリンクで遊べるが発見されない。

### プレミス審査で難しかったところ

「高校生」「student」「trainee」は 8 ジャンル中 2 つの**普通の語彙**なので、単語一致では使えない。
組み合わせ規則にした: 未成年マーカー + 性的語 → ブロック、強い未成年マーカー(明示的な 18 歳未満、
「小学生」)+ 恋愛語 → ブロック。同様に「how to make X」も、名詞ではなく**形**で判定する — 覚醒剤を
題材にした犯罪ドラマは作れるが、作り方は聞けない。過剰ブロックを防ぐ許可側のテスト表を必ず添えている。

## 12. ジェムの入手経路が無かった — **解消**

ジェムはスキーマにもウォレットにも台帳にもあったが、**入る経路が連続ログイン報酬だけ**だった
(週 35)。120 ジェムのワールドは 3.5 週間かかる計算で、実質誰も studio に到達しない。
ウォレット作成時に 120(初日に 1 個だけ作れる)と、消耗型のジェムパック 3 種を足した。
課金側は非サブスクの購入を記録だけして**何も付与していなかった**ので、そこも塞いだ。

## 13. プレミス審査が 1 層だった — **解消**

決定的な語彙照合は、無料で即座で、ジェムを 1 つも使う前に走る点で第 1 層として正しい。
が、言い換えには弱い。実際、20 件のプローブで 2 件抜けていた(第4次 11 節)。

モデル分類器を第 2 層として **AND** で足した。設計上の要点：

- **決定的層がブロックの最初と最後の権限を持つ。** ブロック時はモデルを呼ばない
  = 拒否されるプレミスはトークンを 1 つも使わないし、モデルがブロックを緩めることは構造上できない。
- **軽量ティア・小さいキャッシュ接頭辞(約 430 トークン)・max_tokens 64。** 毎回の作成試行で走るので。
- **プレミスはシステムブロックに入らない。** `sanitizePremise` を通してユーザーブロックの引用柵の中。
- **障害時は決定的層の答えに縮退**(`LLM_PREMISE_SCREEN_ON_ERROR=block` で反対のトレードも選べる)。
  プロバイダ障害を「誰も世界を作れない」に変換するのは自傷であり、プレミスは依然として第 1 層・
  全プロンプトの安全ブロック・全アクションの G8・公開前の人間審査に晒される。
  ただし**モデルの拒否(refusal)はブロック扱い** — 拒否はネットワークではなくその文章への判断だから。

32 件のプローブ(すべて第 1 層が通すもの、半分は 13+ が拒否すべきもの)：
**第 1 層のみ 16/32 → 2 層 32/32**。ゴム印モデルでも第 1 層を下回らないことも確認済み。

### ついでに見つけた過剰ブロック
`suicide` / `自殺` を裸の名詞でブロックしていたため、「10 年前の自殺から立ち直りつつある町」
「自殺に見える死」といったミステリー・日常系の**まっとうな前提が丸ごと落ちていた**。
名詞をソフト扱いにし、教える・演出する・煽る・競う が隣接したときだけブロックする組み合わせ規則に変更。

## 15. 公開後に何も起きなかった — **解消**

`target: "world"` の通報は受理されてテーブルに入るだけで、誰も読んでいなかった。
別人 `REPORTS_TO_PULL` 人で **Explore から自動的に下ろして審査キューに戻す**。

ブリゲーディングとは定義上「同時実行の通報」なので、素朴に数えると 2 つの事故が起きる —
数え落とし(3 人が同時に通報し、各自「自分の 1 件」しか見えず誰も下ろさない)と二重実行。
数える**前に** `SELECT … FOR UPDATE` で World 行をロックし、取り下げは `status='published'`
条件付き UPDATE。**通報数ではなく別人数**を数えるので 1 アカウントでは絶対に下ろせない。
preset は免疫、unlisted は対象外(リンクであって棚ではない)。**下ろされた世界は作成者も
進行中のプレイヤーも遊べる — 取り下げは削除ではない。**

キューも「キュー」にした: 悪いもの順(通報で下りた > 未審査、古い > 新しい)、通報件数、待ち時間、
SLA 超過フラグ、そして**苦情の本文**。何に反対されたか読めないレビュアーは当て推量をしている。
却下後の再申請にはクールダウン(安全ゲートの**前**に判定するのでトークンを使わない)。
