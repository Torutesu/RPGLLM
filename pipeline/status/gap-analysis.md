## 対応方針

S0 と S1 は**リリース前提条件**なので全件埋める。S2 は「Status を上回る」ための本体なので、リテンションに直結する S2-1/2/3/6 と成長の S2-4/5 を実装する。S3 は S3-5(コスト可視化)を最優先、次に CI/デプロイ。

実施記録は `build-notes.md` の各エージェント節に残す。

# 対応結果(2026-09-04)

`pnpm --filter api test` **103/103** · `pnpm e2e` **27 passed / 4 skipped / 0 failed** · 全パッケージ typecheck クリーン。

## S0 — 全 7 件 解消

| # | 対応 |
|---|---|
| S0-1 | ワンタイムコード認証(6桁、ソルト付きハッシュのみ保存、10分・5回・使い捨て、定数時間比較)。固定コードは `AUTH_DEV_CODE=1` のときだけ |
| S0-2 | `assertProductionConfig()` — 本番で弱い/既定の `JWT_SECRET`、`AUTH_DEV_CODE`/`TEST_HOOKS`/`BILLING_MODE=test`/`ADS_MODE=test` のいずれかが有効なら起動を拒否 |
| S0-3 | `.env.example` は非本番でのみ読み込み。適用したファイルをログに出す |
| S0-4 | トークンバケット方式のレート制限(認証 5/分、書き込み 20/分、広告 10/分、その他 120/分)。429 + `Retry-After` |
| S0-5 | `CORS_ORIGINS` の許可リスト。`*` は `TEST_HOOKS=1` のときのみ |
| S0-6 | 固定広告トークンは `ADS_MODE=test` 限定。それ以外は AdMob SSV 署名検証(失敗時は拒否) |
| S0-7 | `?token=` は `GET .../stream` の 2 本のみ |

アカウント削除(30日猶予 + purge)、データエクスポート、同意設定(未成年は強制オフ)、通報(本文スナップショットはサーバ側で解決)、ブロック(フィード・DM・**生成キャストから実際に除外**)、設定画面、法務リンク、購入復元導線。削除済みアカウントは `requireAuth` が 410 を返す(復元のみ例外)。

## 残課題

1. **Batch ティアが未対応** — ゲートウェイに batch 経路が無く、`cost-architecture.md` §5.4 の 50% 割引(雑談・記憶統合・ダイジェスト・評価)が効いていない。**唯一の設計未達**
2. **スケジューラが無い** — `runOfflineDirector` / `runMemoryConsolidation` / `runAmbientRefill` を cron から呼ぶ必要がある
3. **ログインコードがインメモリ** — 単一プロセス限定。Redis か DB テーブルへ
4. プッシュ認証情報、`expo-notifications` の実配線、`PUBLIC_APP_URL`
5. RevenueCat の webhook / restore の実装(現在はスタブ)
6. Docker イメージ未検証(サンドボックスに Docker デーモンが無い)
7. **再生成呼び出しは元のアーム名のまま上位モデルで走る** — 将来のバンディット報酬計算では `escalatedFrom IS NULL` で除外すること
8. `rpgllm_test` は共有のため、テストの並列実行は互いを壊す
9. Lint 負債 317 件(warn)。`apps/mobile` は未 lint
